# Правила работы с репозиторием DeskBot

Эти правила действуют для всего репозитория. Проект — публичный дневник
разработки физического прототипа на ESP32-S3, а каталоги `DeskBot_vXX` —
самостоятельные исторические версии прошивки.

## Версии и область изменений

- Не переписывайте старые версии под текущее поведение. Исправляйте старую
  версию только при явной ошибке, проблеме безопасности или поломанной сборке.
- Новую функцию оформляйте в следующем каталоге `firmware/DeskBot_vXX`.
- Имя каталога обязано совпадать с именем главного `.ino`.
- При добавлении версии обновляйте таблицы в `README.md` и
  `firmware/README.md`, а также создавайте README самой версии.
- Не меняйте распиновку и аппаратные пределы без явного описания миграции.

## Публичность и секреты

- Считайте каждый отслеживаемый Git файл публичным.
- Никогда не коммитьте Wi-Fi SSID и пароль, координаты установки, локальные IP
  устройств, Tuya Local Key, session key, токены, приватные ключи, сертификаты,
  дампы Serial, голосовые записи и персональные датасеты.
- Локальные настройки храните только в `Secrets.h` и `TuyaSecrets.h`. В Git
  добавляйте лишь обезличенные `*.example.h` с явно фиктивными значениями.
- Не включайте `LYNKTUYA_DEBUG`: отладочный вывод upstream может раскрывать
  производный session key.
- Перед коммитом проверяйте `git status --short`, `git diff --cached` и имена
  новых файлов. Если секрет уже попал в коммит, сначала отзовите или замените
  его, затем очищайте историю; простого удаления файла недостаточно.

## Код

- Сохраняйте стиль существующего Arduino C++: два пробела для отступа,
  `constexpr` для констант и явные единицы в именах (`_MS`, `_HZ`, `_MM`).
- Настраиваемые публичные пороги держите в `Config.h`; приватные параметры — в
  локальных secrets-файлах.
- Основной `loop()` должен оставаться неблокирующим. Сетевые и тяжёлые операции
  выполняйте через существующие задачи и очереди FreeRTOS.
- Не добавляйте частый Serial-вывод в аудиотракт и горячие циклы. Диагностику
  делайте событийной или ограничивайте по частоте.
- Учитывайте совместное использование I2C, I2S, PSRAM и GPIO. Изменения аудио,
  сервоприводов или датчиков проверяйте на конфликты ресурсов.

## Документация

- README пишите по-русски, в UTF-8, короткими проверяемыми формулировками.
- Для каждой версии описывайте возможности, оборудование, распиновку,
  зависимости, настройку, сборку, проверку на устройстве и известные риски.
- Ссылки на локальные файлы должны вести только на файлы, публикуемые в Git.
- Не выдавайте успешную компиляцию за аппаратную проверку. Явно разделяйте
  подтверждённые результаты, ожидаемую диагностику и ещё не выполненные тесты.

## Проверка изменений

- Собирайте затронутый скетч командой из его README или эквивалентной командой
  `arduino-cli compile` для ESP32-S3 N16R8.
- После изменений поведения выполняйте перечисленные в README физические тесты;
  если платы нет, помечайте их как невыполненные.
- После правок README проверяйте локальные ссылки и соответствие команд,
  распиновки и параметров фактическому коду.
- Перед публикацией повторно проверяйте текущее дерево и всю Git-историю на
  секреты и приватные данные.
